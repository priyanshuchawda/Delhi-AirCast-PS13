DELHI AIRCAST
PS-13 AI-POWERED AIR QUALITY FORECASTING
PROJECT SHOWCASE AND COMPLETION REPORT

A complete data-to-dashboard air-quality forecasting project
Prepared: 9 October 2026
Project repository: https://github.com/priyanshuchawda/Delhi-AirCast-PS13

======================================================================
PROJECT AT A GLANCE
======================================================================

Delhi AirCast is an end-to-end air-quality forecasting system built for
Delhi. It brings together public environmental data, carefully constructed
time-series features, comparative machine-learning experiments, AQI
calculations, model-serving APIs, interactive dashboards, and portable
container deployment.

The project delivers two complementary forecasting experiences:

1. HISTORICAL CPCB STATION FORECASTING
   A research pipeline for 39 Delhi monitoring stations, producing direct
   PM2.5 concentration forecasts at 1, 3, 6, 12, and 24 hours. The feature
   workflow combines station history, nearby monitors, weather, atmospheric
   model fields, and regional fire activity. Comparative experiments selected
   gradient-boosted trees as the practical model family for the demonstrated
   historical task.

2. LIVE TWO-STATION PILOT
   A live-data experience for Pusa and R.K. Puram using the WAQI station feed.
   It fetches current observations, uses an independently trained history-
   aware model, and reports forecasts on the WAQI/US-EPA individual PM2.5
   index scale.

Together these tracks demonstrate a full applied AI workflow: source data,
quality checks, time-aware feature engineering, baseline comparisons, advanced
model challengers, API inference, user interfaces, and deployment packaging.

======================================================================
PROJECT OBJECTIVE
======================================================================

The PS-13 problem is to make short-term air-quality information more useful
and local for people in Delhi. A city-wide daily average cannot describe every
monitoring location or the way pollution changes over the next several hours.
Delhi AirCast addresses this need with station-aware near-term forecasts,
historical context, pollutant summaries, and clear visual presentation.

The project combines applied machine learning with a practical engineering
system. It includes both offline research forecasts built from historical
CPCB/OpenCity station data and a separate live pilot connected to WAQI. Its
interfaces make the timing, data source, station, forecast horizon, and AQI
interpretation visible to users.

END-TO-END ARCHITECTURE
======================================================================

The system is organized as a clear progression from source data to the
forecast experience:

PUBLIC DATA SOURCES
    |
    v
SOURCE-SPECIFIC ACQUISITION
    |  resumable downloads, API pagination, retries, manifests, hashes
    v
NORMALIZATION AND PROVENANCE
    |  canonical field names, UTC/IST timestamps, units, missing values
    v
QUALITY AUDITS
    |  coverage, duplicates, station registry, coordinates, network health
    v
POINT-IN-TIME FEATURE DATASETS
    |  historical station data + weather/CAMS/FIRMS as available at issue time
    v
MODEL TRAINING AND EVALUATION
    |  chronological splits, persistence comparisons, station-aware metrics
    v
MODEL ARTIFACTS AND SERVING BUNDLE
    |  per-horizon weights, feature schemas, compact inference snapshots
    v
FASTAPI AND DASHBOARDS
       station forecasts, AQI results, history, maps, live pilot, source labels

The live pilot follows its own serving path. The API retrieves the two WAQI
feeds server-side, checks freshness, builds features from collected readings,
uses the live-index model, and returns attributed results to the web interface.
This keeps its index-scale prediction separate from the CPCB concentration
forecast pipeline.

======================================================================
DATA SOURCES AND THEIR CONTRIBUTION
======================================================================

CPCB / OPENCITY DELHI HOURLY ARCHIVE
The principal supervised source for historical station modelling. Its station
measurements provide the pollutant labels and station-level observations. The
project documents 78 source resources and 39 station files in its 2024–2025
normalized panel.

CPCB DATA.GOV.IN LIVE SNAPSHOT
Provides a route for official current station readings and metadata. The
project includes a resumable API connector and uses conservative station
matching to support quality reports and coordinate metadata.

OPEN-METEO HISTORICAL WEATHER
Provides central-Delhi hourly temperature, relative humidity, precipitation,
wind, pressure, and cloud cover. These fields add meteorological context to the
historical feature workflow.

OPEN-METEO AIR QUALITY / CAMS
Provides regional atmospheric-model pollutant fields used as auxiliary
predictors. The project accounts for the product's publication delay before
joining these fields to forecast issue times.

NASA FIRMS ACTIVE-FIRE OBSERVATIONS
Provides MODIS and VIIRS fire detections across Delhi and surrounding regions.
Normalized daily counts and fire-radiative-power summaries contribute regional
event context to the historical modelling experiments.

OPENAQ
Provides an API workflow for Delhi/NCR sensor catalogs, latest values, and
hourly data. The project preserves location, sensor, parameter, unit, and
coverage information to support comparison and validation workflows.

IIT DELHI AIRDELHI
Provides mobile-sensor and spatial-grid data for a distinct spatial research
layer. It is normalized independently from reference monitor observations.

KAGGLE / HUGGING FACE DATASETS
Provide comparison and provenance-review sources. Dataset roles are documented
so that community derivatives remain identifiable and auditable.

WAQI LIVE STATION FEED
Provides the current PM2.5 individual index for Pusa and R.K. Puram in the live
pilot. Its index semantics are kept separate from concentration and CPCB AQI.

======================================================================
DATA ACQUISITION AND ENGINEERING
======================================================================

ACQUISITION
The general downloader discovers and downloads OpenCity resources and obtains
historical weather, CAMS data, and CPCB reference documents. Dedicated
connectors handle the sources that need their own API protocols:

- OpenAQ acquisition retrieves catalogs and hourly batches with paging,
  request pacing, retries, external key handling, and resumable manifests.
- NASA FIRMS acquisition divides the requested date range into short windows,
  supports retry/resume, and stores checksummed raw CSV responses.
- CPCB live acquisition supports paginated snapshot collection.
- Kaggle acquisition uses the external Kaggle client and keeps credentials
  outside the project repository.

NORMALIZATION
CPCB/OpenCity CSVs are mapped into consistent pollutant and meteorological
field names. Timestamps are parsed to UTC while local Indian Standard Time is
also available. Numeric columns are normalized, provider sentinel values are
converted to missing values, and measurements are resampled to hourly
observations with within-hour sample counts. The project retains a pollutant
reading only when the configured sample minimum is met.

OpenAQ hourly JSON is normalized into a long-form Parquet table with sensor,
location, parameter, unit, coverage, and source-time fields. Duplicate sensor
and timestamp records are collapsed deterministically. FIRMS detections are
parsed into UTC event times, coordinates, confidence, satellite, and fire
radiative power. Daily aggregates summarize Delhi and surrounding regions.

DATA QUALITY AND COORDINATES
The station-panel audit generates machine-readable coverage, station registry,
network coverage, and quality summaries. Coordinate matches are conservative:
unique station matches are accepted, while an unmatched station is left
unassigned rather than given an estimated location.

The documented panel run contains 39 station files and 684,216 hourly rows
from 1 January 2024 to 31 December 2025. Mean network hourly PM2.5 availability
is reported as 93.20%, and 38 of the 39 station names match coordinates from
the live CPCB snapshot.

======================================================================
FEATURE ENGINEERING AND TIME-AWARE DESIGN
======================================================================

CORE STATION AND TIME FEATURES
The multi-station feature builder creates a shared station-hour table. For each
station it includes current PM2.5, PM2.5 lags at 1, 3, 6, 12, 24, 48, and 72
hours, and rolling mean/standard-deviation summaries over 3, 6, 12, 24, and 72
hours. Other pollutant and local meteorology fields include current values and
selected lags. Time is represented with cyclic sine/cosine encodings for hour,
weekday, and month, along with a weekend indicator.

SPATIAL FEATURES
For each monitoring station, the data builder uses the five nearest stations
from the coordinate registry. At each timestamp it summarizes available
neighbor PM2.5 using mean, maximum, standard deviation, and availability count.
The GNN challenger separately represents the monitor network as nodes and uses
a six-nearest-station graph.

AUXILIARY FEATURES
- Weather is joined using the latest source timestamp at or before the issue
  time. Wind speed and direction are converted to vector components.
- CAMS regional pollutant fields are joined with an explicit six-hour
  publication lag, plus additional lag/rolling values.
- FIRMS data is used only from completed prior days, including regional counts
  and multi-day summaries.

DIRECT TARGETS
The dataset builder creates direct labels at +1, +3, +6, +12, and +24 hours.
Models predict each selected horizon directly, which keeps the prediction
contract straightforward and avoids compounding a chain of earlier predictions.

POINT-IN-TIME DESIGN
Features describe observations available at or before issue time t. Targets
are future values at t+h. Weather joins run backward in time, CAMS carries a
publication-delay rule, and fire summaries use complete earlier days. The
training and evaluation partitions are chronological, and neural preprocessing
is fitted from training data. These design choices make the experiments
appropriate for forecasting evaluation.

======================================================================
MODEL DEVELOPMENT AND NEW MODEL EXPERIMENTS
======================================================================

1. PERSISTENCE BASELINE
Carries the current reading forward. This creates a simple and meaningful
reference for every horizon and helps quantify the value added by learned
models.

2. SINGLE-STATION HISTGRADIENTBOOSTING BASELINE
An early one-hour forecast for site_105 demonstrated the first complete
feature-build/train/evaluate/serve path. It used numeric features with adequate
coverage and a chronological train/validation/test scheme.

3. MULTI-STATION XGBOOST
The project then pooled records across stations and trained direct-horizon
boosted-tree models. This allowed the model to learn shared patterns while
including station identity and local context. Evaluation stored station-level
metrics as well as aggregate scores.

4. UNIFIED-FEATURE FINAL XGBOOST
The final historical model family combines station/time/neighbour features
with point-in-time weather, CAMS, and FIRMS features. The code trains a
separate XGBRegressor for each horizon. Documented parameters include a
squared-error objective, 350 estimators, learning rate 0.05, maximum depth 8,
minimum child weight 8, row subsampling 0.9, column subsampling 0.85, L2
regularization 2, histogram tree building, and random seed 42. Each saved
bundle stores its feature schema and issue-time policy alongside the model.

5. XGBOOST FEATURE-FAMILY ABLATIONS
A diagnostic compared CPCB sensor/time/neighbour features against successive
addition of weather, CAMS, and FIRMS. It also compared XGBoost with
HistGradientBoosting and explored a simple blend selected on validation data.
This makes the contribution of feature families and model complexity visible.

6. EXPANDING-WINDOW BACKTESTS
Five quarterly test windows begin at October 2024, January 2025, April 2025,
July 2025, and October 2025. Each fold expands the training period and scores
the next three months, providing an evaluation across multiple seasonal
periods and station slices.

7. LSTM SEQUENCE MODEL
The LSTM challenger consumes contiguous 48-hour histories in the documented
comparison. Inputs include current PM2.5, neighbor summaries, weather, and
cyclic time. Missing-value indicators are included. A two-layer LSTM with 64
hidden units, dropout, station embeddings, and a direct regression head learns
from sequence order. Training-only normalization and a log1p target transform
support stable optimization.

8. TEMPORAL CONVOLUTIONAL NETWORK
The TCN uses residual temporal convolution blocks with multiple dilation
levels to model patterns over different portions of the history. It shares the
sequence input/cohort design with the LSTM and produces a direct horizon
prediction with station embeddings.

9. SPATIAL GRAPH NEURAL NETWORK
The GNN represents each coordinate-matched CPCB monitor as a graph node.
Six-nearest-station edges pass information between nearby monitor states. A
learned node representation and message-passing layers combine local recent
conditions with spatial context. Validation-based early stopping chooses the
checkpoint; the test comparison uses common station-time rows against XGBoost
and persistence.

10. FIVE-POLLUTANT AQI FORECAST EXPERIMENT
Separate direct-horizon models estimate PM2.5, PM10, NO2, CO, and O3. The
project's CPCB sub-index calculation combines the forecast concentrations into
a five-pollutant AQI subset. The experiment also compares against a
PM2.5-only proxy and persistence on a matched cohort.

11. LIVE WAQI HISTORY/SPATIAL MODEL
A separate HistGradientBoosting model family predicts the WAQI individual
PM2.5 index proxy for Pusa and R.K. Puram. Features include current index,
cyclic local time, station identity, hourly index lags through 72 hours,
rolling statistics, and the contemporaneous reading from the other pilot site
when available.

12. LIVE WAQI WEATHER CANDIDATE
The live pilot also evaluates weather inputs. The API uses weather only from
at or before the WAQI issue timestamp and requires it to be fresh. A recorded
promotion gate compares validation and test performance; the eligible weather
models are used at the horizons selected by that gate.

======================================================================
AQI ENGINE AND INTERPRETATION
======================================================================

The AQI module defines CPCB concentration breakpoints for PM2.5, PM10, NO2,
SO2, O3, CO, and NH3. It calculates pollutant sub-indices and uses the largest
available sub-index for a composite result when sufficient inputs are
provided. It returns a clear insufficiency status when a composite cannot be
calculated. A PM2.5-only result is explicitly named a derived proxy.

The project therefore distinguishes three kinds of values:
- PM2.5 concentration in micrograms per cubic metre.
- CPCB AQI calculated from available pollutant concentrations.
- WAQI individual PM2.5 index on the WAQI/US-EPA scale.

These distinctions are reflected in API response fields and dashboard labels,
so users can understand the scale of each result.

API AND APPLICATION EXPERIENCE
======================================================================

FASTAPI ENDPOINTS
- GET /health — reports API and model/data readiness.
- POST /aqi — calculates pollutant sub-indices and AQI/proxy status.
- GET /stations — returns station registry and available latest offline data.
- GET /stations/forecast — returns forecasts for available stations at a chosen
  horizon.
- GET /forecast/{station_id} — returns a station-specific forecast.
- GET /forecast/{station_id}/path — returns forecasts across supported horizons.
- GET /stations/{station_id}/history — returns recent station PM2.5 history.
- GET /live/stations/forecast — returns current Pusa and R.K. Puram WAQI index
  forecasts with freshness, source attribution, and feature mode.

The service loads horizon-specific model artifacts and their feature schemas.
Offline responses identify their historical source status. The live endpoint
validates WAQI timestamps and values, uses server-side credentials, maintains a
short cache, and records new observations for history features.

WEB DASHBOARD
The Next.js application presents a Delhi overview, station selector, horizon
controls, monitor map, forecast AQI and PM2.5 cards, recent history chart, and
pollutant summaries. Its live pilot panel separately shows WAQI readings,
forecast index, observation age, model mode, and a refresh control. SWR handles
fetching and periodic refresh. The API URL is configured through the frontend
rewrite, so browser components use same-origin backend paths.

STREAMLIT RESEARCH DASHBOARD
The local dashboard loads research Parquet and model bundles to explore
stations, forecasts, metrics, and available model comparisons. It supports
side-by-side views of selected tree and neural/graph challengers when their
artifacts are present.

======================================================================
DEPLOYMENT AND REPRODUCIBILITY
======================================================================

The Python service is packaged with uv and Docker. The web frontend uses a
multi-stage Node 22 Docker build and Next.js standalone output. Docker Compose
runs both services, health-checks the API, mounts the offline serving bundle
read-only, and keeps live observation history in its own storage mount.

The serving-bundle builder packages inference-time data and weights without
copying the full research panel into the runtime image. The project also
includes a portable export workflow for launching the dashboard and API on
another machine.

Typical research workflow:
1. Install the locked Python dependencies with `uv sync --locked`.
2. Acquire and normalize data with scripts/download_* and scripts/normalize_*.
3. Audit the station panel with `scripts/analyze_cpcb_panel.py`.
4. Build multi-station and unified features.
5. Train baselines and candidate models.
6. Run chronological, rolling, and feature-family evaluations.
7. Build the compact serving bundle.
8. Start FastAPI and the selected dashboard.

The repository includes unit tests for AQI, API, data construction, source
normalization, and model-evaluation logic. GitHub Actions is configured to
install the locked environment and run the Python test suite.

======================================================================
CONCLUSION
======================================================================

Delhi AirCast demonstrates how a real-world forecasting idea can be developed
into a complete, inspectable software system. The project connects public
data acquisition, time-series data engineering, station-network context,
multiple AI model families, AQI calculations, service APIs, interactive
visualizations, and portable deployment into one coherent workflow.

Its model program is evidence-led: it establishes baselines, measures
boosted-tree performance, tests newer sequence and graph approaches, studies
additional data sources, and records how model choices are made. Its software
architecture separates the historical CPCB research experience from the live
WAQI pilot and carries source and scale information into the user interface.

The result is a strong PS-13 project foundation: a working technical
architecture, a broad set of implemented data and model components, measured
forecasting experiments, and a clear path for continued research and product
improvement.
